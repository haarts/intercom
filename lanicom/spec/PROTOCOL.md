# lanicom protocol, version 1

Normative. The key words MUST, SHOULD and MAY are as in RFC 2119. Test vectors
are in [`vectors/`](vectors/); every implementation MUST pass them.

lanicom is a serverless push-to-talk intercom for one LAN. Every device is an
equal peer. Devices find each other with authenticated broadcast `Hello`
messages and send audio directly to each other over UDP.

## 1. Transport

- All traffic uses UDP port **47100** (configurable; every device in a network
  MUST use the same port). One socket sends and receives both packet types.
- Discovery uses the IPv4 limited broadcast address `255.255.255.255`.
- Optional multicast (section 7) uses group `239.255.76.73` on the same port.
- A packet MUST NOT exceed 1200 bytes. Receivers drop larger datagrams.
- IPv6 is out of scope for v1.

## 2. Keys

Every device in a network shares one **key string**, normally generated by
`lanicom keygen` (25 random base32 characters in five dash-separated groups,
125 bits). Any passphrase works, but a weak one can be brute-forced offline
from one captured packet, despite the PBKDF2 stretching.

Leading and trailing whitespace is stripped. Everything else, including case and
dashes, is significant.

```
master   = PBKDF2-HMAC-SHA256(password = UTF-8(key string),
                              salt = "lanicom-v1", iterations = 100000, dkLen = 32)
prk      = HKDF-Extract-SHA256(salt = "lanicom-v1", ikm = master)
key_id   = uint16_be(HKDF-Expand-SHA256(prk, info = "key-id", L = 2))
send_key(sender_id) = HKDF-Expand-SHA256(prk, info = "packet" || uint32_be(sender_id), L = 32)
```

- `key_id` is public. Receivers use it to drop traffic from other networks
  cheaply before attempting decryption. It also allows a future key rotation in
  which two keys are accepted at once.
- Each sender has its own AEAD key. Two devices that happen to pick the same
  epoch therefore never reuse a (key, nonce) pair.

## 3. Packet format

All integers are big-endian.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | `version` | `1` |
| 1 | 1 | `type` | `1` = CONTROL, `2` = AUDIO |
| 2 | 2 | `key_id` | from section 2 |
| 4 | 4 | `sender_id` | random at first boot, then persisted; never `0` |
| 8 | 8 | `epoch` | unique per sender per boot (see below) |
| 16 | 4 | `seq` | per sender, +1 for every packet sealed in this epoch, starts at 0 |
| 20 | n | ciphertext | |
| 20+n | 16 | Poly1305 tag | |

Packets are sealed with ChaCha20-Poly1305 (RFC 8439), using:

- `key` = `send_key(sender_id)`;
- `nonce` = bytes 8..19 of the header (`epoch || seq`, 12 bytes);
- `aad` = the 20-byte header.

The (key, nonce) pair MUST never repeat, which leads to these rules:

- `seq` is a single counter per sender. It is shared by both packet types and
  by all destinations.
- When a sender sends the same packet to several peers, it seals it **once** and
  sends identical bytes to each peer. This is allowed and is cheaper.
- `epoch` MUST NOT repeat for a given sender. RECOMMENDED: `uint32 boot_counter`
  (persisted and incremented before the first packet of a boot) `||` `uint32
  random`. Hosts without persistent storage use 64 random bits. Before `seq`
  would wrap, the sender MUST pick a new epoch.

### Receive procedure

A receiver processes each datagram in this order, stopping at the first
failing step. Every drop is counted per reason, and none produces a reply
except where noted:

1. The length is at least 36 and at most 1200, `version == 1`, and
   `type` is known. Otherwise drop (`malformed`).
2. `key_id` equals ours. Otherwise drop (`foreign`).
3. `sender_id` is not our own. If it is and `epoch` equals ours, this is our
   own broadcast looping back: drop it silently. If it is with a different
   epoch, another device has the same id: drop it, and if the packet also
   authenticates, pick a new random `sender_id`.
4. Open with `send_key(sender_id)`. If this fails, drop (`auth`).
5. Epoch verification (section 4). Packets from an unverified epoch are only
   used as described there.
6. Replay check against the sender's verified epoch (section 4). Duplicates
   and too-old packets are dropped (`replay`).
7. Update the peer's address (source IP and port) and `last_seen`, then
   dispatch on `type`.

## 4. Epoch verification and replay protection

An attacker on the LAN can record packets and send them again later. A
per-epoch sliding window (64 packets) catches replays within one epoch.
Without further checks, though, a receiver that never saw an epoch, or that
rebooted since, would accept a whole recorded session. Epoch verification
closes that gap with a challenge that needs no clock:

- Each peer entry has a `verified_epoch` (initially none).
- When an authenticated packet arrives from an epoch other than
  `verified_epoch`, the receiver does this:
  - **Hello with `echo` equal to the challenge pending for that peer:** set
    `verified_epoch` to the packet's epoch, start a fresh replay window at its
    `seq`, clear the challenge, and process the Hello normally.
  - **Anything else:** send that peer (at the packet's source address) a
    unicast Hello with a fresh random non-zero 64-bit `challenge`, at most once
    per 250 ms per peer. Create the peer entry if it is new. Then drop the
    packet, except that a Hello's own `challenge` field (if any) is still
    answered, as below. Nothing else changes.
- A Hello carrying `challenge = c` is always answered with a unicast Hello
  whose `echo = c`, sent from the current epoch, even if the challenger is not
  verified yet. Replies are limited to 10 per second per source address.
- The replay window keeps the highest `seq` seen and a 64-bit bitmap of the
  64 `seq` values below it. A packet more than 63 behind the highest is
  dropped as too old. A packet whose bit is already set is dropped as a
  duplicate.

Two peers meeting for the first time thus verify each other within two round
trips, in practice when the first `Hello` is seen and long before anyone
talks. A rebooted sender's first audio frames arrive before peers have
verified its new epoch only if it talks within about 1 ms of booting.

**Residual risks (accepted for v1):**
- Every holder of the network key can impersonate any `sender_id`. There are no
  per-device identities; this is a non-goal.
- `key_id`, sender ids, epochs, packet sizes and timing are visible, so traffic
  analysis can tell who is talking to whom.

## 5. Control messages

The CONTROL plaintext is one protobuf `Control` message, as defined in
[`lanicom.proto`](lanicom.proto). Unknown fields MUST be skipped.

### Discovery and liveness

- A device sends a `Hello` (with no `challenge` or `echo`) to the broadcast
  address at start-up, three times (at 0, 0.5 and 1.5 s). After that it sends
  one every 5 s, with ±1 s random jitter.
- It also sends `Hello` to any statically configured peer addresses on the same
  schedule. This is for networks where broadcast doesn't reach, such as across
  routed VLANs.
- A peer is forgotten after 30 s without a verified packet, or immediately on
  a verified `Hello` with `bye = true`.
- `name` is a display name (UTF-8, ≤ 32 bytes). A changed name takes effect
  with the next `Hello`.
- `caps`: bit 0 `PLAYBACK` (plays audio), bit 1 `CAPTURE` (can talk), bit 2 `MONITOR`
  (wants talk metadata for every stream, e.g. Home Assistant, without receiving audio).

### Talk metadata

- `TalkStart {target, stream_id}` is sent just before each of a stream's first
  three audio packets, and `TalkStop {stream_id}` three times after its last
  one. Both go by unicast to every recipient of the stream and to every
  verified peer with `MONITOR` set, whatever the target. They are never sent
  by multicast.
- These are **informational** (for UI, LEDs and Home Assistant events). Playback
  MUST NOT depend on them: a stream starts with its first audio packet and ends
  after 300 ms without audio, or on `TalkStop`.
- Receivers dedupe both on (sender_id, stream_id).

## 6. Audio

The AUDIO plaintext is:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `stream_id`, random per talk spurt (never 0) |
| 4 | 4 | `ts`: timestamp of the first sample, in 48 kHz ticks, random start, +480 per 10 ms |
| 8 | n | exactly one Opus packet (n ≥ 1) |

- **Codec:** Opus, mono. Senders SHOULD encode at 16 kHz in VOIP mode with
  in-band FEC enabled, 10 ms frames (20 ms is allowed, for example to halve the
  packet rate on Wi-Fi), at 16 to 24 kbit/s.
- Receivers MUST accept 10, 20, 40 and 60 ms frames. They get the frame length
  from the Opus packet itself.
- The jitter buffer orders frames by `ts`. It MUST NOT use the header `seq`:
  that counter also advances for packets sent to other peers, so gaps in it say
  nothing about loss.
- On a missing frame, the receiver decodes the next frame's in-band FEC if that
  frame is already buffered, and uses Opus PLC otherwise.
- Concurrent streams are mixed (summed with saturation). There is no floor
  control.

### Addressing

A talker resolves its `Target` against its peer table at send time:

- `device`: that peer.
- `all`: every peer.

To reach a set of devices, a talker sends one stream to each of them: the same
stream, sealed once per recipient (see below).

It only includes peers that have `PLAYBACK` set and are verified. It seals each
frame once and sends a copy to every peer in that set (unicast fan-out).

## 7. Multicast (optional)

A device MAY enable multicast. It then joins `239.255.76.73` and sends frames
for target `all` to the group once, instead of fanning out. Devices that don't
enable multicast never receive multicast audio. A network should therefore
either enable it on every device or on none.

Multicast is meant for wired-only installs. On Wi-Fi, multicast is sent at the
lowest basic rate without retries, and many access points drop or rate-limit
it, so stay with unicast there.
